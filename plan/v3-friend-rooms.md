# v3 規劃：好友房（開房傳連結）＋ 多人（2 人以上）

目標：玩家可以「開房間 → 選一般／惡魔模式 → 把連結傳給好友 → 好友點連結加入 → 人到齊開局」，且一場支援兩人以上同玩。

本文件不是實作規格，而是**動工前需要先想清楚、做出決定的事項清單**。每項附上選項與（若有明顯傾向的）建議。

---

## 0. 範圍切分：要不要一次做到多人？

這是第一個、也是影響最大的決定。「好友房」和「多人化」是兩件事，耦合度其實不高：

| 方案 | 內容 | 改動幅度 |
|---|---|---|
| A. 分兩階段 | Phase 1 先做「兩人好友房」（開房＋連結加入，規則完全不動）；Phase 2 再做多人化 | Phase 1 很小：加房號路由與等待室即可，`Game` DO 幾乎不用改 |
| B. 一次到位 | 直接把 `Game` 多人化，好友房開局人數 2~N | 大：`p1`/`p2` 硬編碼遍佈 `game.ts`、`types.ts`、`public/app.js`、D1 schema，等於協定改版 |

**建議**：A。兩人好友房可以先上線驗證「傳連結找朋友玩」這個需求，多人化牽動規則設計（見第 3 節），值得單獨想清楚。以下第 1、2、4 節適用 Phase 1；第 3、5 節主要是多人化的題目。
> B 一次到位

## 1. 房間建立與加入

### 1.1 房號／連結格式
- 房號用什麼：短碼（如 6 碼、去除易混淆字元 `0/O/1/I`）vs 直接用 UUID？
  - 短碼好唸好傳（可口頭報房號），但要處理碰撞與佔用回收；UUID 零碰撞但連結醜、無法口頭傳。
  - **建議**：6 碼短碼，`crypto` 隨機產生；碰撞機率低，建房時檢查該房是否已在等待中即可。
> 採用短碼（如 6 碼、去除易混淆字元 `0/O/1/I`）
- 連結長相：`https://.../room/ABC123` 路徑式 vs `?room=ABC123` query 式？前者要在 Worker 加路由 fallback 到同一份 `index.html`（目前是 SPA 單頁，query 式改動最小）。
- 房號 → DO 的對應：直接 `GAME.idFromName("room:" + code)` 就能路由到同一個 Game DO，**不需要新的 Room DO**；還是要獨立一個 Room DO 管等待室、開局後才轉交 Game？
  - **建議**：不加新 DO。等待室狀態就放在 Game DO 裡（現有 `status: "waiting"` 概念延伸），少一層轉交。
> 採用不加新 DO

### 1.2 房主與權限
- 誰是房主：建房者。要決定房主能做什麼——選模式？開始遊戲？踢人？
- 模式（一般／惡魔）在**建房時鎖定**，還是等待室內可以改？改了要即時通知已加入者。
  - **建議**：建房時選定、進房後不可改，最單純；連結（或加入畫面）要讓好友**看得到這房是什麼模式**再決定加入。
  > 採用建議
- 房主中途離開等待室：房間解散？還是移交給下一位？（兩人房建議直接解散。）
  > 直接解散

### 1.3 開局時機
- 兩人房：第二人一進來就自動開局（沿用現有行為）？還是也要等房主按「開始」？
  - 自動開局最省事，但好友可能還沒準備好；**建議**兩人房先沿用「到齊即開局」。
- 多人房（Phase 2）：一定需要「房主按開始」或「全員 ready」機制——要選一種。最少開局人數（2？）與人數上限（4？6？8？DO 撐 WebSocket 沒問題，但 UI 和輪轉節奏是限制）要定。
  > 一定需要「房主按開始」

### 1.4 房間生命週期
- 等待逾時：沒人加入多久後房間失效（現有 Lobby 是 30 秒，好友傳連結顯然要更久——10 分鐘？）。用 DO alarm 清理。
  > 採用 10 分鐘
- 連結在**遊戲開始後**或**已滿員**時被點開：回「房間已滿／已開始」錯誤即可？還是允許觀戰（見 6.3）？**建議先回錯誤**。
  > 變成觀戰
- 同一場打完要不要支援「再來一場」（rematch）留在同房？現有 Game DO 結束後狀態是 `over` 且不重開；rematch 需要重置或換新房號。**建議 Phase 1 先不做**，結束畫面給「再開新房」按鈕。
  > 最好是能重置，因為邀請連結可以重複用（但是紀錄希望能個別保留）
- 同一玩家（同 localStorage UUID）開兩個分頁進同一房：要擋（現有隨機配對就有 `p1.id === p2.id` 不計分的處理，但好友房更容易發生）。**建議**：同 id 第二條連線視為重連而非新玩家。
  > 採用建議

### 1.5 私密性
- 連結即權限（知道房號就能進）夠不夠？要不要密碼？**建議**：連結即權限，房號空間夠大、房間有 TTL，不做密碼。
> 採用建議

## 2. 好友房與現有帳號／積分系統的關係

- **ELO 要不要計**：好友房可以互刷（小號餵分）。選項：
  - a) 好友房一律不計 ELO、不計勝敗場——最乾淨，**建議**。
  - b) 只計兩人好友房；多人不計。
  - c) 照計，接受被刷。
- `matches` 與 `game_events` 還是要記（分析用），但要加欄位區分來源：`source: "match" | "room"`（隨機配對 vs 好友房），且多人化後 schema 要動（見 5.3）。
- 排行榜、個人戰績頁要不要顯示好友房場次？（若不計 ELO，建議戰績分開列或乾脆不列。）
> 採用建議 a

## 3. 多人（>2）的規則設計 —— 最需要想清楚的一塊

現有規則全是雙人對稱設計，多人後每一條都要重新回答：

### 3.1 回合順序
- 出手順序怎麼定：加入順？每回合隨機洗牌？固定順序 + 每回合先手輪替（現有 `firstMover` 交替的一般化：round-robin）？
- **建議**：固定座位順序輪流，每回合先手往後推一位。
> 採用建議

### 3.2 挑戰與計分歸屬
現有：挑戰只針對「上一手」，`delta = A − B`，正分給被挑戰方、負分給挑戰方。多人時：
- 挑戰對象仍限定「上一位玩家的那一手」？（自然成立，因為輪到你時上一手就是前一位。）**建議維持**。
- 得分只在「挑戰者 ↔ 被挑戰者」之間流動，其他玩家不動？**建議是**，改動最小、誘因也直觀。
- 但要注意多人下的**策略失衡**：句子越長越容易不合理，排在「容易爛掉的位置」的玩家吃虧；以及兩人可以聯手做球。先接受、觀察數據，還是要設計制衡（例如挑戰失敗的懲罰加重）？**建議先接受**。
> 維持只在「挑戰者 ↔ 被挑戰者」且限定「上一位玩家的那一手」

### 3.3 超時
現有：有額度 +10 秒；沒額度「對方 +3」。多人時「對方」是誰？
- 選項：a) 下一位玩家 +3；b) 其他所有人各 +1～+3；c) 改成超時者自己 −3（可能出現負分）；d) 超時者本回合跳過、不給分。
- **建議**：d 或 a。b 會讓分數膨脹速度隨人數變化，c 引入負分要改 UI 與勝利判定。
> 兩人以上改成 d，如果跳過只剩下一個人，該人 +3 分

### 3.4 勝利條件
- 先到 5 分：人數越多、每人得分機會越少，一場會拖長。目標分數要不要隨人數調整（如 `TARGET = 5` 固定 vs 隨人數遞減／遞增）？還是改成「固定回合數，最高分勝」？
- 平手怎麼辦（多人下同分到達的機率變高）？
> 兩人以上改成固定回合數（可能5回合），最後看總分排行

### 3.5 中離與斷線
現有：任一方斷線 → 對方直接判勝。多人顯然不能這樣：
- **建議**：中離者移除出局（輪到他時自動跳過），剩最後 1 人才直接結束；剩 2 人時退化回現有規則。
- 中離者的分數要不要保留在計分板上？中離發生在「輪到他」的當下，回合怎麼接續？
- 要不要給重連寬限期（例如 30 秒內重連回來保留席位）？現有雙人版是立即判負；多人版斷線成本低，**建議加寬限期**，但這會讓狀態機多一個「席位懸空」狀態，複雜度不小——也可以先沿用「斷線即出局」。
> 採用建議

### 3.6 惡魔模式的節奏
- 限制累加目前是「本回合每接 5 個字 +1 限制」。多人時句子長得更快，限制堆疊速度變快——門檻要不要隨人數調整（如每 `ceil(2.5 × 人數)` 字）？
- 超時額度（每人 2 次）維持 per-player 不變即可。
> 先不用改累加規則

### 3.7 LLM 成本
- 多人一場的挑戰次數會變多（人多、回合多），OpenRouter 花費上升。現有 `ai_costs` 記錄可先估算單場成本，決定要不要對多人房設限（例如每場挑戰上限）。**建議先不管，靠既有成本紀錄觀察。**
> 建議先不管

## 4. 進場流程與前端 UX

- 首頁入口變成三個動作：**隨機配對**（現有）／**開房間**／**加入房間**（貼房號或直接點連結進來）。版面要重排。
- 等待室畫面（新）：房號與模式顯示、已加入玩家列表、「複製連結」按鈕（手機上優先用 Web Share API `navigator.share`，桌面 fallback 複製到剪貼簿）、（多人）開始按鈕。
- 點連結進來但**還沒設暱稱**的新玩家：要先走現有的暱稱輸入流程，再進等待室——順序要接好。
- 多人對戰畫面（Phase 2）：計分板從左右兩欄變成 N 人列表、「輪到誰」的高亮、結算畫面（挑戰者／被挑戰者是誰）的呈現方式，手機直式空間怎麼擺。
- 結束畫面：多人的名次呈現（只有第一名？還是全排名？）。
> 全部排名

## 5. 技術面改動（Phase 2 多人化的成本清單）

這節列的是「決定做多人後就躲不掉」的重構，先知道量體：

### 5.1 `Role = "p1" | "p2"` 一般化
- `types.ts`、`game.ts`（825 行中大量 `role === "p1" ? "p2" : "p1"` 的對偶邏輯）、`public/app.js` 全部要改成 seat index（`0..N-1`）或 player id 導向。
- `Scores { p1, p2 }` → `number[]` 或 `Record<playerId, number>`；`timeoutQuota` 同理。
- WebSocket tag／attachment 現在存 `"p1"/"p2"`，改存 seat。

### 5.2 WebSocket 協定改版
- `start`／`update`／`settled`／`gameover` 訊息裡所有 `p1`/`p2` 形狀的欄位（`scores`、`names`、`ratings`、`timeoutQuota`、`elo`）都要改成陣列。前後端要同步改版——要不要留舊協定相容？（**建議不留**：無原生 app、前端同倉庫同時部署，直接切。）
- 新增等待室訊息：`roomState`（玩家列表增減）、`kick`／`start` 指令等。

### 5.3 D1 schema
- `matches` 表是 `p1_id/p2_id/winner` 雙人形狀 → 多人需要 `match_players` 子表（match_id, player_id, seat, score, rank），或好友多人場另立一張表。需要一次 migration（`migrations/0002_*.sql`）。
- `game_events` 的 `p1_score/p2_score` 快照欄位同樣是雙人形狀，多人事件的比分快照怎麼記（JSON 欄位？）。
- ELO 若決定好友房不計（第 2 節），`elo.ts` 可不動。

### 5.4 路由與 Lobby
- `Lobby` DO（隨機配對）完全不動。
- Worker 新增：`POST /api/room`（建房，回房號）＋房號加入走現有 `/game/:id/ws`（id 換成 `room:CODE` 的 DO name）即可；或加一個 `GET /api/room/:code` 查房間狀態（存在？模式？人數？）給加入前的確認畫面用。

## 6. 先明確排除（或延後）的範圍

決定「不做什麼」跟決定做什麼一樣重要，建議明文排除：

1. **帳號系統升級**：仍沿用 localStorage UUID，不做登入。
2. **聊天／表情**：等待室與對戰中都先不做溝通功能（好友通常本來就在同一個聊天群）。
3. **觀戰模式**：連結被第三人點開先回「房間已滿」；觀戰是獨立功能，之後再說。
4. **自訂規則**（目標分數、秒數、超時額度、限制種類開關）：先全部用預設值，只開放「一般／惡魔」一個選項，避免等待室變設定頁。
5. **Rematch 同房再戰**：先用「再開新房」替代。

## 7. 建議的決策順序（TL;DR）

1. 先拍板 **第 0 節**：分兩階段（建議）還是一次到位。
2. Phase 1（兩人好友房）只需再決定：房號格式（1.1）、模式鎖定時機（1.2）、房間 TTL（1.4）、ELO 計不計（2）——都拍了就能動工，改動集中在 `index.ts` 路由、`Game.fetch` 的加入邏輯、前端首頁＋等待室。
3. Phase 2（多人化）動工前必須先回答：3.2 計分歸屬、3.3 超時、3.4 勝利條件、3.5 中離——這四題定案後，5.1–5.3 的重構才有規格可依。
